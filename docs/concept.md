# 家計の見通し帳 コンセプト

> **先が見えるから、今を気持ちよく使える**

画面や機能を変えるときの判断の基準にするメモ。2026-11 にユーザーと話して決めた内容をまとめている。
仕様の細部は [design.md](design.md)、使う人のイメージは [personas.md](personas.md) を参照。

## 一言でいうと

**ざっくり計画して、ちゃんと振り返って、お金の使い方を良くしていく。大きい出費は先に見えていて安心。**

- 軸は **計画 → 使う → ふりかえる → 次の計画を良くする** というサイクルが回ること。
- **細かく管理したいわけではない**。数字をぴったり合わせることは目標にしない。
- 安心の源は、正確な数字ではなく、**大きい出費が先に分かっていること**と、**計画にだいたい余裕があること**。
- 迷ったら、「細かさ」を足す前に「サイクルが回りやすくなるか」を考える（→ 4章）。

## 1. このアプリで叶えたいこと

| 気持ち | このアプリでどうしたいか |
|---|---|
| 未来のお金の流れを分かりやすく管理して、安心したい | 半年〜1年先まで、大きい出費を見通せるようにする（細かい収支の予測ではない） |
| 「何に使ったか」だけでなく、「どういう計画で、何に使いすぎたのか」を考えたい | 計画とのずれを見て、理由を振り返れるようにする |
| 何でもかんでも節約しよう、というのは嫌 | ずれに種類をつけて、見直すのは「なんとなく」の分だけにする |

### 理想の月

**計画どおりに積み立てて、決めたお金を気持ちよく使って、だいたいプラマイゼロで終わる**こと。

- これは理想の**イメージ**で、**数字の目標ではない**。ぴったり ±0 にすることや、余りを出すことは目指さない。
- 「余り」や「行き先が決まっていないお金」を細かく見せて、合わせさせるような画面にはしない。
- 貯金と投資はまとめて「**積み立て**」と呼ぶ（「貯まる」だと投資が入らないため）。

### 主役にしないこと

- **「今月足りるか？」**: 気にならないわけではないが、主役ではない。先の見通しの中で自然に分かれば十分。
- **節約の押しつけ**: 使いすぎを赤字や警告で責めない。大事なことに使ったお金は「納得のずれ」として認める。
- **日々の支出の記録**: 家計簿アプリ（Zaim など）に任せる。このアプリは、月ごとのカテゴリの合計を受け取るだけ。
- **銀行・カード・家計簿アプリとの API 連携**: スコープを広げすぎないために持たない（データの方針とも合わない → 1.1）。

### 1.1 データの方針

- 最終的にはスマホアプリにする。
- 運営側はデータベースを持たない。データは**使う人のスマホの中**に置き、バックアップや端末間の引き継ぎは iCloud など、使う人のクラウドに保存する。
- 今の Web 版も、データはブラウザの中（IndexedDB）だけに置いている。この方針を崩す機能（サーバーへの保存、外部サービスとのログイン連携など）は入れない。

### 1.2 スマホアプリ化の方針（2026-11-11 に決めた。まだ着手しない）

**今は Web 版で使い心地を考えるフェーズ**。画面と考え方が固まったら、iPhone アプリに移る。

| 論点 | 決めたこと | 理由 |
|---|---|---|
| 作り方 | **Swift（SwiftUI）で作り直す**。今の Web 版は仕様書兼お試し版にして、最終的には閉じる | iCloud での複数端末の同期（最低限は自動バックアップ）が欲しい。SwiftData と CloudKit ならサーバーなしで同期できる。iPhone らしい見た目と操作にもなる |
| 見送った方法 | Capacitor（WebView で包む）、React Native、Flutter | WebView は iPhone らしさ・キーボードまわり・ウィジェットとのデータ共有が弱い。どれも iCloud の同期はプラグイン頼みで、2台で触ると変更が消えやすい |
| 端末 | iPhone と iPad。**Android は出さない** | iCloud の同期は Apple の端末どうしだけ |
| データ | SwiftData + CloudKit。使う人の iCloud に置き、運営側は持たない | 1.1 の方針どおり |
| バックアップ画面 | iCloud の自動バックアップ（オン／オフ、頻度）、今すぐバックアップ、ファイルで書き出す（共有シート）、ファイルから読み込む、バックアップ履歴、の構成にしたい | ユーザーが参考に挙げた家計アプリの画面のイメージ |
| 開発の進め方 | Mac がないので、**GitHub Actions の Mac**で組み立て・テスト・シミュレーターのスクリーンショットを撮る。実機は **TestFlight** で試す | iPhone だけで最後まで進められる |
| Apple Developer Program | **まだ登録しない**。シミュレーターで作り、実機で触りたくなったら登録する（年会費は登録日から1年） | 無料の Apple ID では、Mac なしで実機に入れられず、iCloud も使えない |
| リポジトリ | **新しいリポジトリ**を作る。コンセプトと設計書はそちらに移して正にする。今のリポジトリは、Web 版を閉じるときにアーカイブする | Web 版を閉じたときに、アプリ側がきれいなまま残る |
| 公開・非公開 | **作っている間は公開、App Store に出す前に非公開**にする。一度公開したものは取り消せないので、見られて困るものは入れない | 公開なら GitHub Actions の Mac が無料で使い放題。非公開だと無料プランでは月200分ほど（1回10〜20分）。非公開にする理由はセキュリティより、まねされないため（サーバーがなく、鍵は Secrets に入れるので、公開しても危ないものはない） |

着手するときの順番: 新しいリポジトリを作る → 土台と GitHub Actions（シミュレーターで組み立て・スクリーンショット）→ 計算とテストを Swift に移す（今のテストを答え合わせに使う）→ 画面（ホーム → ふりかえり → 計画 → 設定）→ Apple Developer に登録 → TestFlight と iCloud の同期。

## 2. 3つの柱

### ① 見通す（半年〜1年）

- 毎月の収入・支出に加えて、**大きい出費**を計画に入れておく。
  - 例: 旅行・家電の買い替え・家の更新料・車検・年会費などの年払い
- 「いつ、何に、いくら」が先まで見えていることが、安心につながる。
- カードの請求は、使った月の翌月以降に自動で入る。

### ② ふりかえる（毎月）

- 月末に、家計簿アプリのカテゴリ別の合計を入れて、計画とくらべる。
- 見るのは「いくら使ったか」より、**計画とのずれ**。
- ずれには種類をつけて、理由を一言メモできる（→ 3章）。
- ふりかえりは反省会ではなく、**次の計画を良くする時間**にする。

### ③ 将来を試す（数年〜数十年。今後の展望）

- 今の計画を続けたら、貯金がどうなっていくかのシミュレーター。
- ①の計画と②の実績が、そのまま材料になる。
- 今すぐは作らない。①②のデータの持ち方を決めるときに、つなげられるようにしておく。

## 3. ずれの考え方

### 3.1 ずれの種類

「使いすぎ」とは呼ばず、**計画とのずれ**と呼ぶ。

| 種類 | 例 | 次にすること |
|---|---|---|
| 納得 | 旅行・趣味など、大事なものに使った | 次からは計画に入れる |
| 想定外 | 病院・冠婚葬祭など | 予備費を考える |
| なんとなく | 気づかないうちに増えていた | ここだけ見直す |

- **予算より少なく済んだ月も、ずれとして扱う**。「思ったより使わなかった」も、計画を見直す材料になる（予算を減らす、ほかに回す など）。

- 理由は、「旅行」「友だちの結婚式」くらいの**一言のメモ**で十分。
- 後から振り返るとき（「この月はこれだったな」）の手がかりになる。

### 3.2 ずれた分を、どこから払ったか

払い方によって、その後への影響が違う。

| 払い方 | その後への影響 | アプリでの扱い |
|---|---|---|
| カード | 翌月以降のカード請求に入る | 見通しに自動で反映される。追加の操作はいらない |
| 貯金から崩す | 毎月のお金の流れには影響しない。そのかわり貯金が減る | 記録できるとよい。「貯金を増やすか」を考えるきっかけにする |

### 3.3 残高は持たず、動きだけを見る

- このアプリは**お金の動き（流れ）を扱い、残高（ストック）は持たない**。
  - 残高を手で合わせ続けるのは面倒で、合わせないと実際とずれて気になるため。
  - 正確な残高を見るのは、銀行アプリや資産管理アプリの役目にする。
- 貯金について見せるのは、次のような**増えた・減った**だけ。
  - 今月の動き（「今月は +3万円」「今月は貯金から2万円崩した」）
  - 使い始めてからの累計（「この1年で +28万円」）
  - 先の見通し（「今の計画を続けると、1年後には +36万円」）
- 投資の値動きや利息は入れない。「計画どおりに貯めているか」を見るためのもの。
- 将来のシミュレーターでは、今の貯金を**そのとき、だいたいの額で入れてもらう**。保存して合わせ続ける数字ではなく、計算の前提として扱う。

## 4. 迷ったときの判断の基準

画面や機能を足すとき・変えるときは、次を確かめる。

0. **計画 → ふりかえり → 改善のサイクルが回りやすくなるか**。
1. **先が見えて、安心につながるか**。「今月」だけを見る機能になっていないか。
2. **責めていないか**。ずれや使いすぎを、赤字や警告だけで伝えていないか。
3. **次の計画に活かせるか**。ふりかえりで分かったことが、計画に戻っていくか。
4. **記録の手間を増やしていないか**。日々の記録は家計簿アプリに任せ、ここでの入力は月に数回で済むか。
5. **細かくしすぎていないか**。金額をぴったり合わせることを求めていないか。大きいずれだけ見えれば十分ではないか。
6. **だれのための変更か**。[personas.md](personas.md) の A〜D のだれが得をして、だれがつまずくか。

## 5. 今のアプリとの差

| | 今（2026-11 時点） | 目指す形 |
|---|---|---|
| ホームの主役 | 今月のバッファ（いくら残るか） | 今サイクルのどこにいて次に何をするか、前回のふりかえりで分かったこと、この先の大きい出費 |
| 大きい出費 | 「毎年◯月」の定期項目か、その月だけの項目として入れる | 計画の中心として扱い、先の予定として見える |
| 予算の意味 | 守る上限 | 「ここまでは使っていい」という自分への許可 |
| ふりかえり | 予算との差。超えたら赤 | ずれの種類と一言メモ |
| 貯金から崩した分 | 扱っていない | 記録して、貯金の動き（増えた・減った）として見せる |
| 将来のシミュレーター | なし | 今後の展望 |

## 6. 決まったこと

- アプリの軸は「ざっくり計画して、ちゃんと振り返って、使い方を良くしていく」。細かく管理すること、数字をぴったり合わせることは目標にしない（2026-11-10）
- ホームは、計画 → ふりかえり → 改善のサイクルが回る画面にする。並びは「今やること」「先月のふりかえり（ずれの種類・一言メモ）」「改善のヒント（続いているずれ）」「この先の大きい出費」。余りの推移や、±0 の細かい表示は出さない（2026-11-10）
- 理想の月は「計画どおりに積み立てて、気持ちよく使って、だいたいプラマイゼロ」。数字の目標ではなくイメージ。貯金と投資はまとめて「積み立て」と呼ぶ（2026-11-10）
- 予算より少なく済んだ月も「ずれ」として扱う（2026-11-10）
- 運営側はデータベースを持たず、データは使う人の端末とクラウド（iCloud など）に置く。API 連携はしない（2026-11-10）
- 貯金の残高は持たず、動き（増えた・減った）だけを見る。シミュレーターでは、そのとき、だいたいの額を入れてもらう（2026-11-10）

## 7. まだ決めていないこと

- 「計画とのずれ」として出す大きさ（今は、計画の1割か1,000円の大きい方をこえたもの。オーバー上位3つ・少なく済んだ上位2つ）

- ずれの種類を、カテゴリごとに付けるか、月全体で付けるか
- ウォークスルーの説明（予算・給料日・ふりかえり）を、新しい機能に合わせていつ言い直すか
